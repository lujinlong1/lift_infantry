# 上阶梯分段调试

## 已保存的基线

抬升基线提交为 `8dc63ab`。先验证补偿后的实际行程和保持能力，再验证前进与收杆。当前 `test_start` 是独立抬升测试，会进入 `TEST_HOLD`，不会自动执行上阶梯。

前组为 lift ch0/ch1，后组为 lift ch2/ch3。抬升电机通道与底盘驱动电机 CAN ID 是两套定义，不可混用。

## 完整流程与验证顺序

| 顺序 | 现有状态 | 动作 | 进入下一步的条件 |
| --- | --- | --- | --- |
| 1 | PRECHECK / LIFT_CLEARANCE / VERIFY_CLEARANCE | 四杆伸出到配置高度并保持 | 在线、限位、实际位置与速度检查通过 |
| 2 | APPROACH_STEP (4) | 第一段低速前进 | 底盘停止后，确认前轮已经到台阶承重位置 |
| 3 | VERIFY_FRONT_SUPPORT (5) | 等待前轮承重确认 | 操作手实际确认；一次确认只用于这一阶段 |
| 4 | SEEK_FRONT_CONTACT / RETRACT_FRONT / VERIFY_FRONT_RETRACT | 收前杆，后杆保持 | 前组到位并稳定，组内一致性通过 |
| 5 | ADVANCE_MIDDLE (9) | 第二段低速前进 | 底盘停止后，后轮到台阶承重位置 |
| 6 | VERIFY_REAR_SUPPORT (10) | 等待后轮承重确认 | 操作手实际确认 |
| 7 | RETRACT_REAR / VERIFY_REAR_RETRACT | 收后杆 | 后组到位并稳定 |
| 8 | FINAL_ADVANCE (13) | 第三段前进，车身完全上阶梯 | 配置距离完成、底盘停止 |
| 9 | COMPLETE (14) | 完成并记录 | 本轮结果核对 |

上述流程现在通过 `stair_start` 接入三段自动前进：沿用已确认的四个底盘驱动电机，以带极性的轮编码器平均增量估计前进距离，到距离后停止驱动，轮速稳定 100 ms 才推进。`sequence_drive_done` 已改为消费后清零的单周期请求；调试正常使用自动距离完成，不需要手工填写它。

现有前轮接触高度和收回高度是占位参数，不能直接认为符合本车台阶几何；独立抬升测试使用的 8/2 mm 也不能直接作为完整流程的最终标定。开始整车收杆测试前，需要核对实际承重点、收回余量和台阶高度。

## Debug 操作

下面字段都在 `g_lift_control_debug`，可在 Watch 展开后编辑。新代码需要先编译、烧录，再重新进入 Debug。

| 字段 | 用法 |
| --- | --- |
| `test_height_mm` | 完整流程的抬升高度；本次验证 200 mm 时填写 200 |
| `stair_distance_mm[0..2]` | 三段总距离，单位 mm；默认全为 0，允许先启动抬升，到对应前进段自动暂停等待输入；前进时允许 1..2000 |
| `stair_speed_mm_s[0..2]` | 各段前进速度，单位 mm/s；默认 50，允许 10..200 |
| `stair_contact_mm` | 前组收回时的中间接触高度；默认 8 是占位值，需要核对承重点几何 |
| `stair_retracted_mm` | 收回目标；默认 2 mm |
| `stair_start` | 填 1 启动完整流程，自动清零；不要同时写 `test_start` |
| `test_start_result` | 1 接受；8 距离、速度或底盘标定非法；9 底盘离线/仍在运动；其余沿用独立抬升结果 |
| `test_pause` | 填 1：停止底盘驱动，四杆保持当前编码器位置；暂停等待不计入阶段超时 |
| `test_resume` | 暂停时填 1：前进段重新读取当前段距离/速度，校验后继续剩余路程；收杆等阶段继续原目标；无自动重试 |
| `sequence_confirm` | 只在状态 5 或 10、实际确认对应轮组已经可靠承重后填 1 |
| `stair_drive_leg` | -1 非前进阶段，0/1/2 表示当前前进段；前进暂停期间仍显示对应段号 |
| `stair_drive_progress_mm` | 当前段估计距离；暂停保留，进入下一段重新清零 |
| `stair_drive_target_mm` | 当前段已接受的总距离；输入非法时保留原目标，新段等待输入时为 0 |
| `stair_drive_waiting_input` | 1：当前前进段尚未接受有效距离/速度；填写对应数组项后置 `test_resume=1` |
| `stair_drive_input_result` | 0 尚未输入；1 接受；2 等待输入或距离/速度非法；3 轮子仍在运动或同时请求暂停/中止；离线看 `stair_drive_stop_reason` |
| `stair_drive_stop_reason` | 0 正常，1 驱动电机离线，2 两秒无足够前进增量，3 反向超过 10 mm；异常停止后需检查再恢复 |
| `stair_retracted_mask` | 已收回并锁存电流归零的轴掩码，前组为 3、四轴为 15 |
| `stair_drive_release` | 仅在 IDLE / COMPLETE 时填 1，归还底盘给遥控；完成/故障不会自动恢复摇杆驱动 |

启动复用静止在线检查、临时软件零点与 200 mm 行程补偿。底盘方向和距离系数在接受启动时保存。各段距离和速度在进入该段时读取，也可以在该段暂停后重新输入，再通过 `test_resume=1` 接受。修改 Watch 数值本身不会唤醒暂停或改变正在运动的当前段。

### 先启动，再逐段输入

1. 进入 Debug 并运行程序，核对抬升高度、接触高度和收回目标。保留三段 `stair_distance_mm` 为 0，写 `stair_start=1`，四杆先抬升。
2. 抬升完成后，第一段距离为 0，自动进入 `TEST_PAUSED (17)`，底盘停止，抬升保持当前编码器位置。此时 `stair_drive_leg=0`、`stair_drive_waiting_input=1`。暂停期间等待输入不计入阶段超时。
3. 在 Watch 写 `stair_distance_mm[0]` 为本段预计总距离（mm），再写 `test_resume=1`。有效范围 1..2000，速度有效范围 10..200 mm/s。输入非法或底盘未停稳时保持暂停，请检查结果字段，再主动恢复。
4. 需要在前进过程中调整时，先写 `test_pause=1`，等底盘停稳，再改当前段数组项并写 `test_resume=1`。已走路程会保留：例如已经走 40 mm，想再走约 110 mm，就填写总距离 150 mm。填小于已走路程的正数不会倒车，恢复后静止稳定 100 ms 即完成本段。
5. 第一段到位后仍需在状态 5 确认前轮可靠承重：写 `sequence_confirm=1`，然后收前杆。第二段到来时，如果 `[1]` 仍为 0，会自动暂停；按相同方法填写 `[1]`、恢复。第二段完成后在状态 10 确认后轮可靠承重，再收后杆。
6. 第三段到来时填写 `[2]`、恢复，完成整车上阶梯。三段含义分别是：前轮到位、后轮到位、车身完全上台阶。也可以在进入下一段之前填写它的距离，进入该段会按此值自动前进。

当前段的距离只在该段前进或前进暂停期间调整；到距离后进入承重确认/收杆阶段，已经完成的前进段不能通过修改距离重新执行。需要追加路程时请在该段完成之前暂停调整。调试采用逐段输入时，每轮启动前把待输入段重新设为 0；上轮填写的数值不会自动清除。

底盘接管期间忽略遥控速度与小陀螺。命令超过 100 ms 未刷新或任一驱动电机离线，底盘停止输出，不自动恢复遥控。两秒前进不足 2 mm，或出现反向运动，会请求完整流程暂停；抬升轴堵转也会进入带电暂停。已收回组到目标附近的电流逐轴锁存为零，另一组仍由控制器保持；暂停不会把仍承重的四杆一起断电。

轮胎打滑会造成距离差异，必须逐段实测修正；电机转动距离不等同于整车实际位移。首次只填保守的距离并逐段验证，接近需要观察的位置先暂停再调整总距离；进入承重确认阶段时先停下观察，需要超过 60 s 检查时先暂停。距离和收杆动作验证完成后，再将相同接口映射到遥控器。

## HardFault 排查与栈修复

若当前执行位置在 `stm32f4xx_it.c` 的 `HardFault_Handler` 死循环，启动请求不会被消费，此时继续写 `stair_start` 或点击 Run 不能让任务恢复。截图中 `stair_start=1`、`test_start_result=0` 就是请求未处理的表现。

目标调用图报告 `lift_control_task` 已知最大栈深度为 4208 字节，原静态任务栈只有 4096 字节，没有覆盖调用链，更没有为 RTOS/FPU 上下文和未报告调用留余量。这是已确认的软件容量缺口；截图本身尚不能证明故障指令的具体原因。现已把抬升任务栈扩大为 8192 字节，保留运行时距离输入功能。

重新编译并下载修复后的固件，然后复位重新开始 Debug。核对 `test_start=0`、`test_height_mm=200`、三段距离为 0，再单独写 `stair_start=1`。接受后请求应清零、`test_start_result=1`，先抬升再等待距离输入。修复前的故障上下文不能通过 `test_resume` 或 `sequence_reset` 恢复。

每次修改任务代码后，先完成 Keil 构建，再运行 `powershell -ExecutionPolicy Bypass -File Tests/Lift/check_stack_budget.ps1`。脚本读取目标调用图和 map，核对实际链接的任务栈，并要求已报告最大深度之外至少保留 1024 字节。静态检查不能覆盖未知调用、间接调用或运行时栈破坏，仍需上板复测。

栈修复后 Keil 编译为 0 Error(s)、0 Warning(s)，目标链接的抬升任务栈为 8192 字节、报告最大深度为 4208 字节，容量检查通过。固件源码主机编译检查通过；目标日志在 `_staging/stair-stack-fix-keil.log`。本次修改仅扩大静态栈，不改变运动流程；新版 HEX 已生成，尚未下载到控制板验证 HardFault 是否消失。
