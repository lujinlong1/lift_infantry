## 1. 八个模块，两个支路

```
  遥控 / 上台阶动作表（lift_seq，LIFT-011）
        │  lift_control_command_t
        ▼
  lift_seq       动作时序执行器：超时 / 到位稳定 / 人工确认 / 中止
        │
        ▼
  lift_top       总编排：持有 homed / zero_ecd，决定走哪条支路
        │
        ├── 未找零 ──► lift_homing ×4 ───────────────────────────┐
        │              每轴一个实例，只在上电找零阶段工作            │
        │                                                        │
        └── 已找零 ──► lift_control ─► lift_sync ─► lift_guard ───┤
                        模态PID+斜坡    模态→电流   限位/缓降/门禁    │
                        复用 pid.c      翘曲恒0                      │
                                                                 ▼
                                                  robot_lift_set_currents()
                                                        → CAN1 0x200

  旁路（不在控制链上）：
    lift_geometry   ecd ↔ um、转速 → um/s          供标定与行程限位换算（LIFT-007）
    lift_telemetry  整数快照 + VOFA+ JustFloat 帧   供上板观测与复盘（LIFT-012）
```

**`lift_top` 是固件任务唯一需要调用的入口。**
**`lift_seq` 只是产生命令的一种来源**——手动遥控是另一种来源，调用方按
`lift_seq_is_active()` 在两者之间切换。

阶段一（手动拨杆逐步操作）可以**完全不接** `lift_seq`；它是为将来的
"一键上台阶"准备的。这也回答了第 6 节的第 4 个问题：两种方式不冲突，
手动先做，时序后加。

**分层规则（违反即为设计缺陷）**

| 规则 | 原因 |
|---|---|
| 固件任务只调 `lift_top`，不直接调下面的模块 | 状态只有一份，避免两处各自记账 |
| 控制层不得绕过 `lift_guard` 直接下发 | 限位与缓降是最后一道闸 |
| `lift_sync` 的反变换**没有**翘曲输入口 | 过约束只能靠"不去控制"来避免（ADR-008） |
| 未找零前不得输出任何运动电流 | 没有位置基准就没有安全边界（ADR-007） |
| 四个通道必须**全部**找零成功才算 homed | 只成功三个时第四个没有基准，整车不得运动 |
| 重新找零必须两步：先 clear 再 request | 禁止在已找零状态下直接重新找零，那会在无限位保护下下行 |
| 任何异常一律电流归零并**锁存**，须显式复位 | 瞬时故障不得让抬升永久瘫痪，也不得被自动忽略 |

## 2. 每个控制周期的数据流（建议 5 ms）

```
调用方（固件任务）负责：
    1. robot_motors_get_snapshot() → 抬升组 4 轴的 total_ecd / speed_rpm / online
    2. 由时间戳算出 command_fresh（复用 robot_motor_commands.c 里
       command_is_fresh() 的同款写法，本层不自己读时间）
    3. 组一个 lift_top_input_t，调一次 lift_top_update()
    4. 把 status->output_current[4] 交给 robot_lift_set_currents()

lift_top 内部：
    未找零支路：lift_homing[i].update(...) → 每轴电流 → 直接进 output
    已找零支路： homed_pos[i] = total_ecd[i] - zero_ecd[i]
                 → lift_control_update → lift_sync_distribute → 饱和到 int16
                 → lift_guard_update → output
```

## 3. 模块接口摘要

### 3.1 `lift_homing` — 上电堵转找零（单轴）

```c
IDLE --start--> SEEK --确认堵转--> BACKOFF --退出死点--> DONE
                 |                     |
                 +------- 异常 ---------+--> FAULT（电流归零，须 reset）
```

到达死点的判定**三个条件缺一不可**：

1. 已走出 `seek_min_travel_ecd` 以上行程 → 防止刚上电误判
2. `|speed_rpm| <= stall_speed_rpm`
3. 上述状态连续保持 `stall_hold_ms`

任一反馈丢失、超时、被中止 → FAULT。找到死点后回退 `backoff_ecd` 离开死点。

### 3.2 `lift_guard` — 安全闸

按优先级依次执行：

1. **离线保护**：任一轴反馈丢失 → 全组归零 + 锁存
2. **找零门禁**：未找零 → 任何运动命令不得通过
3. **受控缓降**：命令超时 → **主动往下走**（绝不是归零），到底后进入 `PARKED`
4. **行程软限位**：已到界且仍向界外推 → 拦为 0；反向放行

```c
DISARMED（未找零） / READY / DESCENDING / PARKED / FAULT
```

> `PARKED` 是为一个具体场景加的：上电找零完成后丝杆停在底部，
> 此时还没有任何人下过运动命令，`command_fresh` 天然为 false。
> 一个想当然的实现会立刻进入"超时 → 缓降"，然后超时报故障——可什么都没坏。

方向符号：限位与缓降都按 `direction[i] × sign(current)` 判断，不只看电流符号。

### 3.3 `lift_sync` — 四轴协同 / 过约束保护

核心认识：刚性车身只有 **3 个高度自由度**（高度 / 横滚 / 俯仰），
四个丝杆提供 **4 个**，多出来的第 4 个叫**翘曲**。翘曲的正确控制量是**零**。

矩形布局权重（通道顺序同 CAN `0x201~0x204`）：

| 通道 | 高度 | 横滚 | 俯仰 | 翘曲 |
|---|---|---|---|---|
| 0 右前 FR | +1 | −1 | +1 | +1 |
| 1 左前 FL | +1 | +1 | +1 | −1 |
| 2 左后 RL | +1 | +1 | −1 | +1 |
| 3 右后 RR | +1 | −1 | −1 | −1 |

四行两两正交、每行范数 = 4。采用**转置伴随**约定（不除以 4）：

```
正变换  M = W · x
反变换  c = Wᵀ · U        于是 forward(distribute(U)) = 4·U
```

不除以 4 是为了**整数精确**：反变换里没有除法，翘曲分量严格恒为 0，
不会因整除截断漏出残余内力。

### 3.4 `lift_control` — 模态 PID + 目标斜坡

- 对高度 / 横滚 / 俯仰各跑一个位置 PID（复用工程自带 `pid.c`）
- 目标斜坡限速，禁止目标突变
- **首次使能时斜坡吸附到当前位置**，不是从 0 或旧目标跳过去 → 上电不冲击
- 增益标定提示：单模态指令下模态控制量的数值就等于四轴各自的电流值，
  所以 `pid.output_limit` 可直接按"期望的最大轴电流"设

### 3.5 `lift_top` — 总编排

```c
IDLE（未找零） --homing_request--> HOMING --四轴 DONE--> READY
                     |                                    |
                     +-- 任一轴 FAULT --> FAULT <----------+-- guard FAULT
```

- 输出 `lift_top_status_t`：状态、故障码、`homed`、各轴 `zero_ecd`、
  各轴找零子状态、安全闸状态、最终电流
- 找零完成的那个周期**不输出电流**，让控制支路从下一周期接管（避免交接毛刺）
- 找零完成时自动 `lift_control_reset()` 并重新初始化 `lift_guard`（清其锁存）
- 顶层故障锁存，只有 `reset_request` 上升沿能解；
  已找零时 `reset` 回到 `READY`，未找零时回到 `IDLE`

### 3.6 `lift_seq` — 上台阶动作时序执行器

只做【执行器】，不做具体台阶动作。原因：四个丝杆怎么配合上台阶，取决于行程、
轮径、台阶高度、重心位置——这些机械参数目前还没有。把猜测写死成代码比不写更糟。

```
IDLE --start--> RUNNING --每步到位+稳定--> 下一步 ...
                  |  \-- require_confirm ---> WAIT_CONFIRM --确认--> 下一步
                  |                                        --超时--> FAULT
                  +-- abort --> FAULT
```

三种步骤：`MOVE`（移动到指定模态目标，等到位并稳定）、
`WAIT`（进入时锁定当前姿态并保持，只等人工确认）、`STOP`（结束序列）。

三种"不往下走"的原因分别报不同的错，便于现场判断：
`NOT_HOMED`（没找零就请求）、`STEP_TIMEOUT`（机构没到位 / 卡住 / 操作手忘了确认）、
`ABORTED`（主动中止）。

**⚠️ 集成契约**：本模块只在 `RUNNING` / `WAIT_CONFIRM` 期间把 `command_valid`
置真；序列结束（`DONE`）后立即变为假，调用方**必须立刻**提供新鲜的手动命令。
否则安全闸会在超时后走受控缓降（ADR-006），整车会自己降下来。
手动控制的正确形态是"**增量式绝对高度目标 + 每周期刷新**"，而不是松开就不发。

### 3.7 `lift_geometry` — 位置/速度换算（旁路，不在控制链上）

```
位移_um = ecd × 导程_um × 传动比_分母 / (每圈计数 × 传动比_分子)
```

存在两个理由：

1. `total_ecd -> 毫米` 如果不集中到一处，就会在各处冒出一堆 8192 和"导程"
   的魔法数字，而且没人说得清哪个是对的。
2. C620 反馈的 `speed_rpm` 是**转子侧**还是**输出侧**，目前**没有实机确认**。
   与其在注释里写"待确认"，不如做成一个显式开关 `speed_is_rotor`：
   实机标定时翻一下就完事，不用改公式。

**这个开关绝不是小事**：同一个 `speed_rpm = 100`，两种解释相差约 **19 倍**
（3508 减速比 3591/187）。单测里专门有一条断言把这个倍数钉住。

### 3.8 `lift_telemetry` — 遥测快照与波形帧（旁路）

两件东西：

1. **整数快照 `lift_telemetry_t`**：定义"调试时到底该看哪几个变量"。
   四轴原始位置 / 已找零坐标 / 转速 / 下发电流 / 温度 / 在线、四个模态、
   目标、安全闸与时序状态、以及**累计故障次数**。
   在 Keil 的 Watch 窗口里直接看，或按固定格式记进日志。
2. **VOFA+ JustFloat 组帧**：16 个 float（小端）+ 帧尾 `00 00 80 7F`。
   与工程自带的 `telemetry_task.c` **同一套格式**，所以同一个上位机
   就能同时看 Pitch 和抬升。

通道顺序：`0~3` 四轴已找零位置，`4~7` 四轴下发电流，`8~11` 高度/横滚/俯仰/翘曲，
`12~14` 三个目标，`15` 到位标志。

两个刻意的设计：
- **故障计数只在【跃迁进故障】时 +1**，不是每周期累加——
  否则一次故障在 200Hz 下会变成一串数字，复盘时看不出发生过几次。
- **可观测的不等于可控制**：翘曲模态送上位机是为了**看见**过约束，
  它依然不在控制链上（ADR-008）。

**日志与编号约定**：上板记录沿用本工程既有的 `TEST-YYYYMMDD-NNN` 编号，
写入 `验证记录.md`，原始数据文件同名加 `.csv` 后缀。

| 过约束量化对比 | 地面一角偏 100 计数：模态控制差分电流 0；朴素每轴位置环 225，全部落在翘曲模态上（=纯内力） |

### 未验证（**不得当作已验证**）

- **没有跑过 Keil / 没有进过固件工程**，`Application/Lift/` 尚未建立。
- 没有任何实机数据。所有机械增益、行程、电流都是仿真参数。
- 控制周期 5 ms、任务优先级、栈用量、CPU 占用**全部未测**。
- 悬空未定：抬升组 CAN 报文周期、与底盘任务的执行顺序、加加速度限制（目前只有速度斜坡）。
- `lift_top` 找零完成那一周期的"零输出交接"未在实机上验证是否会引起机构下沉。
- `lift_seq` 的**具体台阶动作表尚未填写**——执行器已就绪，动作表是数据，
  必须等行程、轮径、台阶高度、重心位置确认后由机械与调试共同定稿。
- `lift_geometry` 的**导程与传动比是占位值**，`speed_is_rotor` 的默认取值也未经实机确认。
  标定完成前，任何"毫米"数值都只是估算，不得写进验收结论。

## 6. 待确认的问题（需要你拍板）

1. **四个丝杆在车体上的实际位置**与 CAN `0x201~0x204` 的对应关系。
   若与"0=右前、1=左前、2=左后、3=右后"不一致，改 `lift_sync_config_rect()` 的权重表。
2. **机械侧抱闸/阻尼**：ADR-006 已写明"软件兜不住断电"。这条是否已经提给机械组？
3. **抬升机构的行程**，用来定 `position_max_ecd` 与斜坡限速。
4. **上台阶的操作方式**：操作手手动拨杆逐步操作，还是按一个键走完整套时序？
   这决定 LIFT-011 的状态机复杂度。
