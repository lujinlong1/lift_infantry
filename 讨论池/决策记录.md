## ADR-003：兼容无超级电容与未来超级电容的底盘功率控制

- 状态：已采用（继承，尚未实现）
- 日期：2026-08-05
- 关联议题：LIFT-006 相关
- 决定：第一版可以在无超级电容条件下运行，但功率管理必须预留可插拔的超级电容能量源，
  不得把无超电逻辑写死在底盘控制器中。
- 原因：超级电容是额外能量源，不是底盘功率预测和分配的前提。
- 架构边界：`PowerSource` 负责计算可用功率预算；`PowerLimiter` 统一约束目标电流；
  底盘只提交未限幅目标，不感知是否安装超电。
- 影响与风险：**抬升四个 3508 同时顶起整机时的功率需求远大于底盘行驶**，
  本 ADR 的功率预算模型必须把抬升组纳入，不能只算四轮。该扩展尚未设计。

## ADR-004：以整体复制 + 重命名的方式迁移，不改业务代码

- 状态：已采用
- 日期：2026-09-29
- 关联议题：LIFT-001
- 背景：抬升步兵需要英雄工程的分层骨架（CAN 收发、DBUS、统一发送、PID、遥测），
  但业务模块（云台/发射/底盘）需要按新车重排。
- 决定：第一步**只做整体复制与工程重命名**，一行业务代码都不改；
  基线 Rebuild 的 Program Size 必须与英雄完全一致，以此证明改名是行为中性的。
- 依据：2026-09-29 实测，两边均为
  `Code=81688 RO-data=1744 RW-data=268 ZI-data=90372`，`0 Error(s), 0 Warning(s)`。
- 被否决方案及原因：直接在新目录里"边复制边改"——一旦编译失败，无法区分是改名引入的
  还是业务改动引入的。
- 影响与风险：新工程暂时仍包含 `Devices/DmMotor`、云台、发射等将要删除的模块，
  这是有意的过渡态。
- 验证方式：见 `验证记录.md` TEST-20260929-001。

## ADR-005：CAN1 先"瘦身"再"入住"，不给过渡态引入临时 ID

- 状态：已采用
- 日期：2026-09-29
- 关联议题：LIFT-002、LIFT-004
- 背景：英雄工程 CAN1 的实际组帧是
  `0x200 = {0,0,0,friction[0]}`、`0x1FF = {feeder,friction[1],friction[2],friction[3]}`。
  抬升组要独占 `0x200` 四槽，与 `friction[0]` 冲突。
- 决定：**先做发射系统瘦身**（摩擦轮 4→2、去送弹轮），使 CAN1 `0x200` 变为全空闲，
  再以纯增量方式让抬升组入住 `0x201~0x204`。
- 依据：新车只有 2 个摩擦轮且无独立送弹轮，瘦身本身就是需求，不是为迁移服务的临时手段。
- 被否决方案及原因：
  1. 给 `friction[0]` 临时换 ID 让路——引入过渡态 ID，机械上要重配电调，之后还要再改回去。
  2. 抬升组放 CAN2——CAN2 `0x200` 已被四轮占满，`0x1FF` 剩余空槽不足四路。
- 验证方式：瘦身后 CAN1 `0x200` 帧四路全为 0；加入抬升组后该帧四路对应四个丝杆。

## ADR-006：非自锁丝杆的失联动作是"受控缓降"，不是电流归零

- 状态：已采用
- 日期：2026-09-29
- 关联议题：LIFT-006、LIFT-010
- 背景：机械确认丝杆**不自锁**，静止支撑整机必须靠 3508 持续输出。
  而英雄工程 `robot_motor_commands.c` 的保护策略是
  「命令超过 `ROBOT_MOTOR_COMMAND_TIMEOUT_MS`(100 ms) 未刷新 → 对应电流归零」。
  这道保护对底盘四轮是救命的，对非自锁抬升机构等于"控制任务卡顿一下车身就砸下来"。
- 决定：
  1. 抬升组**不复用**超时归零策略，超时/任务失联/通信异常时的动作是**受控缓降**
     （按限速目标主动向下运动），不是切断输出。
  2. 机械侧必须提供抱闸、摩擦阻尼或单向锁；**软件兜不住断电**，该要求在机械定案前提出。
- 影响与风险：受控缓降需要电，因此"电池被拔"或"电调掉电"这两种情况软件无法处理，
  只能靠机械。抬升组必须单独定义掉电行为并在实机上验证。
- 验证方式：失联测试、任务挂起测试、直接断电测试各做一次，
  记录车身下落高度与冲击（L3 及以上）。

## ADR-007：零位采用"低速堵转找零 + 软件限位"

- 状态：已采用（待实机验证）
- 日期：2026-09-29
- 关联议题：LIFT-005、LIFT-009
- 背景：抬升机构**没有限位开关、没有光电开关、没有绝对位置反馈**，
  3508 的 `total_ecd` 从上电起累计，掉电即失忆。位置控制必须有一个可重复的零点。
- 前提：机械已确认**丝杆两端都有硬死点，顶到底不会损坏部件**。
- 决定：
  1. 上电找零：以受限的小电流、低速度向固定方向运行，检测
     「速度 ≈ 0 且电流达阈值且持续 N ms」判定到达死点，把该点记为行程零点。
  2. 找零必须**限流 + 限时**，超时立即进入故障态，不允许持续硬顶。
  3. 行程保护用软件限位（可参照英雄 `yaw_control.c`/`pitch_control.c` 的软限位写法），
     且必须区分"已找零"和"未找零"两种状态：未找零时只允许找零动作。
- 被否决方案及原因：
  1. 读 Flash 记忆上次 `total_ecd`——丝杆不自锁，掉电后机构会滑动，记忆值不可信。
  2. 靠重力自然落底取零——只在"断电前恰好在底部"时成立，上台阶中途重启即失效。
- 验证方式：连续 10 次上电，记录每次零点对应的 `total_ecd` 离散度（L2 台架）。

## ADR-008：抬升四轴在【模态空间】控制，翘曲模态刻意不受控

- 状态：已采用（待实机验证）
- 日期：2026-09-29
- 关联议题：LIFT-008
- 背景：四个刚性丝杆顶在刚性车身上属于**超静定**结构。若每根丝杆各管各的位置，
  地面稍有不平就会变成巨大内力：电流飙升、抖动、顶坏联轴器。
  这个故障**架空测试永远看不出来，落地才炸**。
- 关键认识：刚性车身只有 **3 个高度自由度**（高度 / 横滚 / 俯仰），
  而四个丝杆提供了 **4 个**。多出来的第 4 个叫**翘曲**，它的正确控制量是**零**。
- 决定：
  1. 控制量定义在模态空间：整车高度、横滚、俯仰三个模态各跑一个 PID。
  2. **翘曲模态不设输入口**——不是在运行时判断它为零，而是接口上根本给不进去。
  3. 坐标变换采用**转置伴随**约定且不做除法：
     `M = W·x`，`c = Wᵀ·U`，于是 `forward(distribute(U)) = 4·U`。
     不除以 4 是为了整数精确：反变换无除法，翘曲分量严格恒为 0，
     不会因整除截断漏出残余内力。
  4. 权重表用四行两两正交的 ±1 基（矩形布局），并提供自检函数。
- 被否决方案及原因：
  1. **四路独立绝对位置环**——四路位置全控就等于把翘曲也控了，必然较劲。
  2. **一主三从**——主机所在那根受载不同就会拖着其余三根走，且引入单点依赖。
  3. **力控均分 + 差分限幅**——能缓解但不能根除，且需要力矩反馈，本车没有。
- 影响与风险：`position_min/max`、方向符号必须逐轴正确标定，标错一根等于标错整个模态分解。
- 验证方式：
  - L1（已完成）：地面一角偏 100 计数时，模态控制差分电流为 0；
    朴素每轴位置环差分电流 225 且全部落在翘曲模态上（纯内力），见 TEST-20260929-002。
  - L3（待做）：实车地面不平时观察四轴电流是否保持均衡。

## ADR-009：抬升控制拆成八个可主机单测的纯逻辑模块，先暂存后集成

- 状态：已采用
- 日期：2026-09-29
- 关联议题：LIFT-005、LIFT-006、LIFT-008、LIFT-009、LIFT-013
- 背景：抬升的安全逻辑（找零、限位、缓降、协同）全部是**上电就决定生死**的部分，
  但它们又都要等设备层（LIFT-004）才能上板。设备层未就绪期间无法验证。
- 决定：
  1. 把抬升控制拆成八个模块：`lift_homing` / `lift_sync` / `lift_guard` /
     `lift_control` / `lift_top`（总编排，固件任务唯一入口）/
     `lift_seq`（上台阶动作时序执行器）/ `lift_geometry`（位置速度换算）/
     `lift_telemetry`（遥测快照与波形帧）。后三个为旁路，不在控制链上。
  2. 四个模块一律为**纯逻辑**：不调用时间函数（`now_ms` 注入）、
     不依赖 FreeRTOS/HAL、不做动态分配，因此可在主机上直接单测。
  3. 主机测试用与学习仓库 C 练习同一套严格标志：
     `-std=c11 -Wall -Wextra -Wpedantic -Werror`。
  4. 在设备层就绪前，模块**暂存在学习仓库**而不写进固件工程，
     避免半成品被误加进 Keil 工程列表；集成时统一移入 `Application/Lift/`。
  5. 主机测试**不进** Keil 工程（含 `main()`，加入会导致链接冲突）。
- 被否决方案及原因：
  1. 直接写进固件等上板再调——安全逻辑没有实机就无从验证，而它恰恰是上电即生效的部分。
  2. 用 FreeRTOS 的 `osKernelGetTickCount()` 取时间——会让模块无法主机单测。
- 影响与风险：主机通过**只等于 L1**，不等于可以在实车上跑。见
  `抬升模块架构.md` 第 4 节「已验证 / 未验证」。
- 验证方式：`TEST-20260929-002`（9 个套件 / 854 项断言 / 零警告）。

## ADR-010：Pitch 换型＝把闭环从电机内部搬回 MCU

- 状态：已采用（**S0-3 实现中**，待实机验证）
- 日期：2026-09-29
- 关联议题：LIFT-003
- 背景：英雄工程的 Pitch 是**达妙 DM6220**，走 MIT 私有帧 `0x001`/`0x011`，
  一帧同时下发 `位置 + 速度 + kp + kd + 力矩`，**闭环在电机内部**。
  新车的 Pitch 是 **GM6020**，走标准 DJI 帧 `0x1FF`，只能下发一个电流（电压）值，
  **闭环必须在 MCU 里做**。
- 关键认识：这不是"换个电机驱动"，而是**控制架构的搬迁**。
  换成 6020 之后，原本由电机内部保证的东西——刚度、阻尼、力矩前馈——
  全部要自己做；增益必须重新调。
- 决定：
  1. Pitch 采用与 Yaw **同构**的串级控制：角度环输出目标转速 → 速度环输出电流。
  2. 删除整个达妙设备层 `Devices/DmMotor/`，以及"离线就重发使能"那条重试链
     （6020 上电即有反馈，不需要使能）。
  3. **保持 `pitch_control` 的对外接口不变**：模式枚举、`effective_min/max_angle_deg`、
     `measured_angle_deg`、`measured_velocity_deg_s`、`online`、`zero_valid`。
     理由是 `remote_control_task.c` 与 `telemetry_task.c` 与电机型号无关，
     不该被牵连。**验收标准就是这两个文件一行都不用改。**
  4. **目标斜坡必须保留**，且做在"命令角度"层（PID 跟踪它），而不是直接喂原始目标。
     闭环搬回 MCU 之后，斜坡从"锦上添花"变成"防阶跃冲击的最后一道"。
  5. 软限位在两种模式下语义不同：位置模式**夹目标**，速度模式只**禁止向外**、
     仍允许反向退出。
- 被否决方案及原因：
  1. **保留 MIT 范式**——6020 只有电流/电压命令，物理上模拟不了位置+增益一帧下发。
  2. **改 remote/telemetry 去适配新接口**——扩大爆炸半径；那两个模块和电机型号无关。
  3. **不保留目标斜坡，靠角度环 PID 自己平滑**——阶跃目标下 PID 输出会先饱和，
     表现为云台"猛冲一下再回来"，且更容易触发限位。
- 影响与风险：
  - 串级两条环的限幅极易配反（外环输出上限应是**转速**，内环输出上限才是**电流**）。
    配错的现象很像"PID 参数不对"，容易在错误方向上调很久。
  - `gear_ratio` 与 `direction` 必须实机标定，不能沿用英雄 DM 的参数。
  - 英雄 Pitch 原有的**绝对位置硬限位**依赖 DM 的绝对位置反馈。
    GM6020 **没有多圈绝对位置**，但它的单圈编码器 `ecd` 是**单圈绝对**的
    ——Yaw 正是靠这一点做"枪管相对车头的角度，不受重新上电影响"
    （`yaw_control.c` 的 `front_ecd` + `yaw_get_front_angle()`）。
  - 因此这条第二道保护**不是消失，而是换了形式**：
    要么改用「单圈 `ecd` + 标定参考点」重建它，要么承认只剩
    「相对上电零点」一道保护——而上电零点在上电瞬间机构停在任意位置时**并不可信**。
    **忽略这一点，才是真正会发生的安全性降级。**
- 验证方式：
  - L0（S0-3）：Keil Rebuild 0 Error / 0 Warning；`remote_control_task.c` 与
    `telemetry_task.c` 一行未改。
  - L3（待做）：实机标定零位、方向、软限位、串级增益；确认绝对限位缺失后的替代保护。
